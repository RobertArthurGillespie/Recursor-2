  ---
  How it works

  Each window the guardrail service checks four signal pairs:

  1. Confusion agreement — does the rule label (confusion/relapse hypothesis) match PredictedConfusionRisk? Falls back to raw
  probability ≥ 0.60 if the confusion model isn't loaded.
  2. Stable mastery agreement — does stable_mastery_pattern match PredictedStableMasteryState? Same fallback.
  3. Hint-dependence risk level — combines HintDependenceProbability (current) and HintDependenceNextProbability (next-window)
   into one of none / low / moderate / high, mirroring the existing guardrail thresholds.
  4. Explicit contradiction — ML says strong mastery but a relapse hypothesis is present.

  Each disagreement adds a plain-English entry to GuardrailWarnings and increments GuardrailConflictCount.
  OverallBehaviorState is then derived by priority: conflicted (≥2 conflicts) → mastering → recovering → struggling → stable →
   unknown.

  The result is logged at Information level per window and persisted to BehaviorStateTrainingRows so it's queryable in KQL
  (e.g. summarize count() by GuardrailOverallBehaviorState).

  ---
  Known limitation / follow-up

  personalizedSignals (user-relative deltas) are fetched later in the pipeline inside the Phase 8 block. The guardrail service
   accepts null for that parameter gracefully, so user-relative anomaly warnings are not populated yet. Wiring that up
  requires either fetching the signals earlier or calling Evaluate a second time after the Phase 8 block. That's a small
  restructure suited for Phase 7D or whenever the first user-relative warning fires.
